# PTT follows the same radio owner as the tune path

Recorded 2026-09-06. Moved verbatim from the desktop CLAUDE.md on 2026-11-09; the original is archived in the potacat workspace at docs/history/CLAUDE-desktop-2026-11-09.md.

**PTT follows the same radio owner as the tune path** — "is this a Flex" for keying means *can the SmartSDR API drive this radio*, never *is `catTarget.type === 'tcp'`* (the SmartSDR-Win CAT shim on 5002-5005). Flex Direct and multiFlex-bound stations drive the radio entirely over the API: `tuneRadio` has keyed off `smartSdr.canTune && (mode === 'self' || !cat || !cat.connected)` since Flex Direct shipped, and JTCAT sends the whole FT8 envelope to the radio as `dax_tx` VITA-49 — but `handleRemotePtt` still asked `catTarget.type`, making it the last Flex control path that never learned. N5ZC (Aurora AU-520, 2026-09-06): POTACAT tuned his radio over the API, streamed every transmission over VITA-49, and then refused to key it — `PTT FAILED: CAT not connected` — because his `catTarget` was a dead rigctld entry. RX, decode and frequency tracking were all perfect, so nothing in the symptom pointed at PTT. `handleRemotePtt` now shares the tune path's predicate exactly; it must NOT be a bare `smartSdr.connected`, because `needsSmartSdr()` also connects for panadapter spots alone and an IC-7300 operator pushing spots to a Flex would have had PTT silently diverted to the Flex. The slice comes from `flexPttSliceIndex()`: the shim port wins when `catTarget` really is the shim (5002=A..5005=D is the operator's explicit declaration, and a station on 5003 must keep keying B even while the host GUI has A active), otherwise `smartSdr.ourSliceIndex` — the old `(catTarget.port || 5002) - 5002` gave slice **-470** for N5ZC's rigctld port 4532, the bug waiting behind the one that bit him. `assertFlexTxDaxForTx()` uses the same resolver so the TX-slice flag and PTT can never name different slices.
